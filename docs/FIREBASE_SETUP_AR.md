# إعداد Firebase لسنونو

يعمل الموقع مباشرة مع Firebase Authentication وFirestore وStorage؛ لا يحتاج خادماً مخصصاً أو Cloud Functions. يستخدم المشروع `taskora-bf729` افتراضياً. إعداد الويب العام ليس سراً، والحماية الفعلية في القواعد وصلاحيات الإدارة.

## قبل النشر على مشروع Taskora المشترك

**لا تنشر ملفات القواعد فوق قواعد Taskora الحالية مباشرة.** نزّل/انسخ القواعد الحالية وادمج أقسام `snounu_*` وأي دوال مساعدة دون حذف مسارات التطبيقات الأخرى. كذلك ادمج إعدادات Hosting والفهارس بدلاً من استبدالها، وتحقق من موقع Hosting المستهدف. ملف `firebase.json` نموذج لإعداد سنونو؛ أمر النشر يغيّر المشروع الحقيقي المحدد في `.firebaserc`.

راجع أيضاً عدم وجود قاعدة عامة قديمة مثل `allow read, write: if true`؛ قواعد Firebase تجمع السماح، وقواعد سنونو لا تستطيع إلغاء سماح أوسع موجود في ملفك. لا توجد صلاحية عامة للمسارات الأخرى في الملفات المرفقة.

## خطوات التفعيل

1. فعّل Firestore وStorage، وAuthentication بطريقة Email/Password وAnonymous من Firebase Console. راجع خطة الفوترة والمتطلبات الحالية للخدمات في وحدة التحكم.
2. أضف نطاق الإنتاج و`localhost` عند الحاجة إلى Authentication → Settings → Authorized domains.
3. أنشئ مستخدم الإدارة من Authentication في Console، وانسخ UID. أنشئ مستند `snounu_admins/UID` يحتوي `enabled: true` من Firestore Console. لا توجد شاشة أو API عامة لمنح الإدارة، ولا يستطيع العميل تعديل تلك المجموعة.
4. جهّز القواعد المدمجة ثم انشرها، واسمح عند مطالبة Firebase بتفعيل وصول قواعد Storage إلى Firestore؛ قواعد رفع الصور تتحقق من مستند المدير في Firestore.
5. شغّل الموقع، ادخل بحساب الإدارة ثم نفّذ زر تهيئة البيانات مرة واحدة. تفتح شاشة الإدارة بإعدادات أولية قابلة للتعديل إذا لم يوجد مستند الإعدادات بعد؛ لا يستخدم الموقع العام هذا البديل. التهيئة ترفض وجود أي منتجات أو فئات أو مكونات أو بنرات أو تقييمات أو رسائل، ثم تتحقق بمعاملة ذرية من غياب الإعدادات وكل مستند مستهدف قبل الكتابة، لمنع استبدال البيانات حتى عند تزامن الطلبات. لا تولّد تقييمات أو رسائل أو حسابات.
6. ارفع الصور من الإدارة. الصور المدعومة JPEG وPNG وWebP وأقل من 5 MiB. يفك المتصفح ترميز الصورة للتأكد من قابليتها للقراءة، ويرفض الأبعاد الأكبر من 8192 بكسل أو 32 مليون بكسل إجمالاً، ثم يصغّرها إلى حد أقصى 2400 بكسل للضلع ويعيد ترميزها WebP لإزالة البيانات الوصفية قبل الرفع. ملفات SVG وGIF وAVIF غير مسموحة. قواعد Storage تتحقق من صلاحية المدير والحجم ونوع MIME؛ لا تتحقق من بايتات الصورة نفسها ولا تفرض إعادة الترميز على عميل مخصص. المحتوى في `snounu/images` عام ولا يصلح لملفات خاصة.

## متغيرات البيئة

يمكن تجاوز القيم الافتراضية في `.env.local` قبل البناء باستخدام:

```dotenv
VITE_FIREBASE_API_KEY=...
VITE_FIREBASE_AUTH_DOMAIN=taskora-bf729.firebaseapp.com
VITE_FIREBASE_PROJECT_ID=taskora-bf729
VITE_FIREBASE_STORAGE_BUCKET=taskora-bf729.firebasestorage.app
VITE_FIREBASE_MESSAGING_SENDER_ID=997225509918
VITE_FIREBASE_APP_ID=1:997225509918:web:3d8317f987cb685544ea0f
VITE_FIREBASE_MEASUREMENT_ID=G-Y0D3NB91P7
```

لا تضع مفاتيح خدمة Admin SDK أو أسراراً ضمن `VITE_*`؛ كلها تظهر في متصفح الزائر. لا تستخدم حساب إدارة مشتركاً ولا تضع كلمة مروره في المستودع.

## القواعد والتقييمات والرسائل

- الجمهور يقرأ المنتجات والفئات والبنرات المنشورة فقط، والمكونات وإعدادات المطعم، والتقييمات الموافق عليها. المدير يقرأ ويدير كامل بيانات سنونو. صاحب التقييم يستطيع قراءة مستنده المحدد بما فيه التقييم المعلّق؛ لا يستطيع سرد التقييمات المعلقة.
- عند الإرسال يبدأ تسجيل دخول مجهول تلقائياً إذا لم يوجد مستخدم. الأخطاء تُعاد للواجهة ولا توجد محاكاة نجاح أو عودة إلى بيانات عرض عند فشل Firebase.
- معرّف التقييم هو `productId_uid`، أي تقييم واحد لكل مستخدم/منتج، من 1 إلى 5، وتعليق حتى 1000 حرف. التقييم الجديد وأي تعديل من صاحبه يعود إلى `pending`، ويجب مرور عشر دقائق بين التعديلات. الخادم يفرض هوية الكاتب وتوقيت الكتابة والمنتج المنشور؛ المدير وحده يوافق أو يرفض. المتوسط المعروض يُحسب من التقييمات الموافق عليها فقط.
- الرسائل خاصة بالمدير، والحقول محدودة ومطلوبة. كل رسالة جديدة تُكتب في دفعة ذرية مع `snounu_submission_limits/uid`؛ القواعد تربط معرّف الرسالة والتوقيت وتمنع إعادة الإرسال لنفس UID خلال خمس دقائق. لا يكفي تعديل فحص الواجهة لتجاوز ذلك.
- لا تُخزّن رسائل البريد في التقييمات؛ UID المجهول موجود في المستند العام عند الموافقة. لا تكتب معلومات شخصية في تعليق عام.
- حدود الإرسال هنا لكل UID وليست لكل إنسان أو عنوان IP. حذف حساب/بيانات المتصفح أو إنشاء هوية جديدة قد يتجاوزها. فعّل App Check للحد من إساءة الاستخدام وراقب حصص الخدمة؛ لا تزعم هذه الآلية منع البريد المزعج بالكامل.

## App Check والتحليلات

لـ App Check سجّل تطبيق الويب مع reCAPTCHA v3 وأضف `VITE_FIREBASE_APP_CHECK_SITE_KEY`. راقب المقاييس أولاً ثم فعّل enforcement من Console للخدمات المناسبة بعد اختبار النطاقات. لا تتضمن الشيفرة مفتاح debug للإنتاج. في وضع المحاكيات لا يبدأ App Check.

لا تبدأ Analytics عند تحميل الصفحة. تستدعي الواجهة `enableAnalytics()` فقط بعد موافقة الزائر الصريحة. راجع نص الخصوصية الفعلي وإعداد الاحتفاظ بالبيانات قبل إطلاق التحليلات.

## الاختبار المحلي

ثبّت متطلبات Firebase CLI وJava المتوافقة مع إصدار المحاكيات، ثم نفّذ:

```powershell
npm install
npx firebase-tools emulators:exec --project demo-snounu --only firestore,storage "npm run test:rules"
```

تختبر الملفات في `tests/rules` منع ترقية الصلاحيات، عزل المسارات، القراءة العامة، تزوير التقييمات والتوقيت والهوية، حدود إرسال الرسائل، وأذونات الصور. فشل بدء المحاكي أو نقص Java لا يعني نجاح القواعد؛ يجب رؤية اختبارات ناجحة قبل النشر. اختبارات Storage تستخدم مشروع محاكاة منفصلاً لعزلها عن اختبارات Firestore.

لتوصيل الموقع بالمحاكيات فقط، ضع:

```dotenv
VITE_FIREBASE_USE_EMULATORS=true
VITE_FIREBASE_EMULATOR_HOST=127.0.0.1
```

ثم شغّل `npx firebase-tools emulators:start --project demo-snounu --only auth,firestore,storage` واضبط `VITE_FIREBASE_PROJECT_ID=demo-snounu`. لا تفعّل هذا المتغير في بناء الإنتاج. لا يحتاج التطبيق فهارس مركبة حالياً لأنه يستعلم بمرشح مساواة واحد ويُرتّب النتائج محلياً.

## النشر بعد المراجعة

ابنِ باستخدام `npm run build`، واختبر الدخول والتهيئة ورفع الصور والإرسال والإشراف يدوياً، ثم انشر إعداد Hosting الصحيح والقواعد المدمجة للمشروع المقصود. لا تنشر على مشروع Taskora المشترك قبل مراجعة الدمج والنطاق وموقع الاستضافة. المشروع لا ينشر نفسه تلقائياً.
